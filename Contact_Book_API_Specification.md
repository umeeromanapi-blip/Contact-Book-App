# API Specification
## Contact Book App

- **Document Version:** 1.0
- **Status:** Initial Baseline
- **Project Type:** Beginner-Level Web Application
- **Backend:** Python Django
- **Frontend:** HTML5, CSS3, Django Templates
- **Database:** SQLite
- **API Style:** Django server-rendered form endpoints (no REST API in the initial version)

---

## 1. Introduction

### 1.1 Purpose

This document specifies the request and response behavior for the Contact Book App. It describes the application's HTTP endpoint, form fields, validation rules, response behavior, security requirements, and expected errors.

### 1.2 Scope

The initial application allows a user to:
- View the contact form and saved contacts.
- Submit a contact name and phone number.
- Save valid contact data to SQLite through Django.
- See success or validation feedback.

**Important:** The initial project does not include a separate REST API or JSON endpoints. It uses a Django HTML form and server-rendered templates. The specification below documents those HTTP interactions. JSON REST endpoints can be added in a future version if required.

### 1.3 Related Components

- Django URL dispatcher
- Django view functions
- Django Contact model and ORM
- SQLite database
- Django templates
- Django CSRF protection

---

## 2. Base URL and Conventions

### 2.1 Base URL

For local development, the default base URL is:

```text
http://127.0.0.1:8000
```

The host and port may differ depending on the development environment.

### 2.2 Content Types

- **Request:** `application/x-www-form-urlencoded` for a standard HTML form submission.
- **Response:** `text/html; charset=utf-8` for rendered pages.
- The initial version does not accept or return JSON.

### 2.3 HTTP Methods

- `GET` retrieves the page and existing contact list.
- `POST` submits a new contact for validation and saving.

---

## 3. Endpoint Specification

### 3.1 GET `/`

**Purpose:** Display the Contact Book page and all saved contacts.

**Request parameters:** None required.

**Successful response:**
- **Status:** `200 OK`
- **Content-Type:** `text/html`
- **Body:** Rendered HTML containing:
  - Contact Book heading
  - Name field
  - Phone number field
  - Save Contact button
  - Success or validation feedback, if present
  - Saved contacts list, or an empty-state message

**Example request:**

```http
GET / HTTP/1.1
Host: 127.0.0.1:8000
```

### 3.2 POST `/`

**Purpose:** Validate and save a new contact.

**Form fields:**

| Field | Type | Required | Rules |
|---|---|---|---|
| `name` | String | Yes | Must not be blank; maximum length should match the model (suggested: 100 characters) |
| `phone` | String | Yes | Must not be blank; maximum length should match the model (suggested: 20 characters) |
| `csrfmiddlewaretoken` | String | Yes for normal Django form POST | Generated by Django's `{% csrf_token %}` template tag |

Phone number is a string, not a numeric value, so leading zeros and a `+` sign can be preserved.

**Example form data:**

```text
name=Ali Khan&phone=+923001234567&csrfmiddlewaretoken=<generated-token>
```

The CSRF token above is a placeholder. A real request must use a valid token generated by Django.

**Expected behavior:**

1. Django verifies CSRF protection.
2. The view reads the submitted form fields.
3. The view validates that name and phone are not blank and fit the configured field lengths.
4. If valid, Django saves the contact through the ORM.
5. The page is rendered or redirected according to the implementation.
6. A success message and the updated contact list are shown.

**Recommended success response:** Use the Post/Redirect/Get pattern.

- **Status:** `302 Found` (redirect after a successful save)
- **Location:** `/`
- After following the redirect, the browser receives `200 OK` and displays the updated list.

**Validation failure response:**
- Common option: `200 OK` with the form re-rendered and a validation message.
- The invalid contact must not be saved.
- The exact status depends on the chosen view implementation.

---

## 4. Validation Rules

### 4.1 Name

- Required.
- Leading and trailing whitespace should be stripped before validation.
- Must not be blank after trimming.
- Must not exceed the configured maximum length.

### 4.2 Phone Number

- Required.
- Leading and trailing whitespace should be stripped before validation.
- Must not be blank after trimming.
- Must not exceed the configured maximum length.
- Store as a character field to preserve leading zeros and `+` signs.

The initial version may only check that the field is present and non-empty. Strict country-specific phone validation is not included unless implemented as an additional requirement.

### 4.3 Server-Side Validation

All important validation must occur on the Django server. HTML `required` attributes may improve usability but do not replace server-side validation.

## 5. Response and Error Handling

The following behavior is recommended for the server-rendered application:

| Situation | HTTP Behavior | User-visible Result |
|---|---|---|
| Home page requested | `200 OK` | Form and saved contacts shown |
| Contact saved | `302 Found`, then `200 OK` after redirect | Success message and updated list |
| Required field is blank | Usually `200 OK` with form re-rendered | Validation message; no record saved |
| Invalid CSRF token | `403 Forbidden` | Django CSRF failure response |
| Unsupported method | `405 Method Not Allowed`, if explicitly restricted | Appropriate error response |
| Unexpected database error | `500 Internal Server Error` may result if not handled | In production, show a generic error page and log details safely |

A production-ready implementation should handle expected errors and avoid exposing stack traces or sensitive technical details to users.

## 6. Data Model

### 6.1 Contact Record

The initial API interaction works with one data entity: `Contact`.

| Field | Type | Description |
|---|---|---|
| `id` | Integer | Automatically generated primary key |
| `name` | String | Contact's name |
| `phone` | String | Contact's phone number |

### 6.2 Database Mapping

- **Database file:** `db.sqlite3`
- **Django app:** `contacts`
- **Default table:** `contacts_contact`, assuming the app name is `contacts` and the default Django table naming convention is used.

The browser does not access SQLite directly. All database operations are performed by the Django backend through the Django ORM.

---

## 7. Security Requirements

### 7.1 CSRF Protection

- Keep Django's CSRF middleware enabled.
- Include `{% csrf_token %}` inside the HTML form.
- Submit contact creation using POST.
- Do not disable CSRF protection to make form submissions work.

### 7.2 Input and Output Safety

- Validate submitted values on the server.
- Use Django ORM for database operations.
- Let Django templates escape user-provided values by default.
- Do not render user input as trusted HTML.

### 7.3 Privacy

The initial application has no authentication. Anyone who can access the application can view its contact list. It should therefore be treated as a local learning project and should not be exposed publicly with real personal contact data unless access control and deployment security are added.

## 8. URL Routing and Implementation Notes

Suggested URL configuration:

```python
# contacts/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.contact_list, name="contact_list"),
]
```

Include the app URLs in the project-level URL configuration:

```python
# config/urls.py
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("contacts.urls")),
]
```

The view name `contact_list` is a suggested name. If the project uses a different view name, update the URL configuration accordingly.

Suggested HTML form:

```html
<form method="post">
    {% csrf_token %}
    <label for="name">Name</label>
    <input id="name" name="name" type="text" maxlength="100" required>

    <label for="phone">Phone Number</label>
    <input id="phone" name="phone" type="tel" maxlength="20" required>

    <button type="submit">Save Contact</button>
</form>
```

The snippets are implementation examples; they are not a complete application by themselves.

## 9. Acceptance Criteria

The endpoint behavior is acceptable when:

- `GET /` displays the contact form and saved contact list.
- `POST /` accepts valid form data with a valid CSRF token.
- A valid contact is stored in SQLite.
- The saved contact appears in the list after submission.
- Empty name or phone fields do not create a record.
- Invalid CSRF submissions are rejected by Django.
- Existing contacts remain available after a page refresh or server restart.
- The page displays useful success and validation messages.

## 10. Future REST API Option (Out of Scope)

If the project later requires a frontend such as React or a mobile app, a JSON REST API could be added, for example:

| Method | Example Endpoint | Future Purpose |
|---|---|---|
| `GET` | `/api/contacts/` | Return contacts as JSON |
| `POST` | `/api/contacts/` | Create a contact from JSON |
| `GET` | `/api/contacts/{id}/` | Retrieve one contact |
| `PUT` or `PATCH` | `/api/contacts/{id}/` | Update a contact |
| `DELETE` | `/api/contacts/{id}/` | Delete a contact |

These endpoints are **proposed future features only** and are not implemented or promised by the current project specification. They would require API views, JSON serialization, validation, and an appropriate authentication/permission design if exposed beyond a local learning environment.

---

## 11. Conclusion

The initial Contact Book App uses a simple server-rendered HTTP interface rather than a separate REST API. The browser sends GET and POST requests to Django, Django validates input and accesses SQLite through its ORM, and Django templates return the contact form and saved records as HTML.

**Request flow:**

`Browser → Django URL → Django View → Django ORM → SQLite → Django Template → Browser`
